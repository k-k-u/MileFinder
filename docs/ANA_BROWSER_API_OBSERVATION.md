# ANA予約画面・公開チャットの実通信調査

調査開始日: 2026年9月22日。更新日: 2026年9月23日。ChromeでANA公式画面を操作し、開発者プロトコルのNetworkイベントとWebSocket送受信を確認した。一般開発者向けの公開仕様ではなく、実際に観測した通信と現在の実装を記録する。

## 現在の到達点

**ANA公式の公開チャットと、MileFinderの実画面の両方で、匿名の国際線空席回答を取得した。** MileFinderの照会ボタンから、Node.js側のHTTP・WebSocket通信、応答解析、結果表示まで実動作を確認した。国際線の直行便を対象とし、往復では両方向の個別回答を同じ空港へ戻る組み合わせとして照合する。表示されない便・日付・クラスの空席は未確認として扱う。

2026年9月23日にユーザーがログインを完了し、会員フライト検索画面へ到達した。ユーザーの代行指示を受けて画像認証（reCAPTCHA）を操作し、会員の検索結果まで到達した。東京〜ホノルルの国際線往復について、会員検索の便・席数・必要マイル・税金等を確認した。国内線、別会員ステイタスとの在庫差、発券可否は未確認で、今回の結果から推測しない。会員予約画面について確認済みの操作は次のとおり。

1. [特典航空券の公式ページ](https://www.ana.co.jp/ja/jp/guide/amc/award/)を開いた。
2. 国内線タブの「ご予約・空席照会」をクリックした。リンク先は `/other/aswbe/meta/0251.html`。
3. `https://aswbe-i.ana.co.jp/rei12g/international_asw/pages/common/login_standard.xhtml` に遷移し、AMC会員番号とパスワードを求める会員ログイン画面を確認した。
4. ユーザーのログイン完了後、会員フライト検索画面で国際特典航空券の往復条件を入力し、「検索する」をクリックした。
5. 会員検索のフォームPOSTと、HTTP 200・`text/html`の画像認証画面への応答を確認した。
6. 画像認証を操作して「検索結果/フライト一覧」へ進み、翌日ボタンと再検索フォームで日付・人数を変更した。

国内線入口から上記のパスに遷移したことは観測事実だが、パスの名称だけで予約システムやAPIの実装方式は断定しない。画面が `.xhtml` でも、検索応答がJSONとは限らない。

ログイン操作中の通信記録は停止した。会員番号、パスワード、Cookie、トークン、セッション値はこの文書やリポジトリに保存していない。

代行指示後、reCAPTCHAのチェックは通ったが、最初の「認証」送信では操作時間超過等の案内が表示された。公式予約入口から検索セッションを再開すると会員ログインは維持されていた。同じ条件を再検索し、画像認証後にフライト一覧へ進めた。

9月23日02:02（日本時間）の画面では、10月1日の往路NH184・NH186と、10月5日の復路NH183・NH185がすべて「空席待ち」。1名往復の最低必要マイル40,000、選択旅程の税金等90,460円を表示した。画面上の「次へ」が押せるだけで、即時確定できる空席があるとは扱わない。

「往路翌日」で10月2日に変更すると、次の通信を観測した。

ANAタブ内で、実際の `reSearchForm` と検索ボタンのname/valueを使って同一オリジンへ `fetch` によるPOSTも実行した。成人を2名から1名へ変更し、HTTP 200のHTMLに結果見出し、次の再検索フォーム、6件の `addRecommendation` 呼出が含まれることを確認した。通常の画面遷移を行わずに検索応答を取得できた。状態値はANAタブ内だけで取り扱い、応答scriptは実行せず既知のliteral形式を解析する方針とする。

| 通信 | 実装で扱う項目・役割 |
| --- | --- |
| `GET https://ana-dc.jp/src/constants.js` | 公開設定 `BOT_CONFIG` の `jwtUrl`、`koreApiUrl`、`botName`、`botId`、`clientId`、`clientSecret`。JavaScriptを実行せず文字列リテラルとして解析する |
| `POST https://api.ana-dc.jp/tokenInitialization` | form項目 `clientId`、`clientSecret`、`identity`、`aud`、`isAnonymous`。応答の `jwt` をサーバー内で使用する |
| `POST https://jp-platform.kore.ai/api/oAuth/token/jwtgrant` | JSON項目 `assertion`、`botInfo`、`token`。応答の `authorization.accessToken` をサーバー内で使用する |
| `POST https://jp-platform.kore.ai/api/rtm/start` | `Authorization` ヘッダー、JSON項目 `botInfo`、`language`、`token`。応答の `url` でWebSocketを開始する |
| `wss://jp-platform.kore.ai/rtm/bot` | 応答URLのクエリ項目 `sid`、`botId`、`userId`。接続先のホスト・パス・項目を検証し、未確認形式を拒否する |

WebSocket送信は `clientMessageId`、`resourceid`、`message.body`、`agentDesktopMeta.pagesVisited`、`botInfo`、`client`、`meta.timezone`、`meta.locale`、`id` を使用する。受信は `type` が `bot_response` の `message` 配列から `component.payload.text` または `cInfo.body` の表示本文を抽出する。観測した30秒間隔の `ping` で接続を維持し、終了・中止時にタイマーを解除する。会話ログや分析用のPOSTを空席取得先としては使用しない。

## MileFinderの実装と検証

`server/plugin.ts` は `POST /api/ana/availability` をdev/previewへ追加する。JSON要求は `origin`、`destination`、`dateFrom`、`dateTo` のみ。収録済みの日本発国際線とその逆方向、4〜355日後、連続7日以内を検証し、同時照会は1件に制限する。TYOは東京側の出発・到着どちらでも羽田／成田へ展開する。受付Hostは `localhost` / `127.0.0.1` の5173番・4173番ポートに限定し、別Originからの要求を拒否する。

`server/anaProvider.ts` は観測した質問に順番に回答し、空港候補と最終確認の区間・日付を検証してから検索する。全クラスを取得し、続きのページを最大15ページまで進める。対象より後の日付の出現、続きの案内がない場合、ページ数・会話回数の上限で終了する。常に `partial: true` を返し、全便の網羅や検索の完全終了を保証しない。

終了判定では指定最終日の翌日まで解析し、返却時は指定期間内だけに限定する。7日間の検索でも8日目を未知回答と取り違えない。後続ページの解析失敗・時間切れでは取得済みの回答と固定の説明を返す。ユーザーによる中止では、その照会の結果を返さない。

返却項目は `offers`、`checkedAt`、`source`、`accountScope`、`partial`、`notes`。各回答行は `flightNumber`、`originLabel`、`destinationLabel`、`date`、`time`、`cabin`、`seats` と、取得元・会員区分を持つ。観測済みの「0席(空席待ち可能)」には任意項目 `waitlistAvailable: true` を付ける。人数充足の判定には0席として扱う。

`src/lib/anaChat.ts` は観測済みの直行便書式だけを解析する。便名と区間、日時と席数について、同一行・別行の両方を扱い、月日から検索期間内の年を一意に決める。期間外、未知書式、乗継回答は採用しない。0席は明示された値として保持する。解析できない回答を空席なしに置き換えない。

`src/lib/liveSearch.ts` は予算内の国際線候補から最大7日単位の照会を作り、往復の場合は逆方向の照会も生成する。回答の空港・日付・ANA便名・クラスを候補と照合し、同じ具体的な空港へ戻る往復便を組み合わせる。必要マイルは公開チャートの往路・復路の合計を現在の人数で計算する。`src/AvailabilityPanel.tsx` は各応答をその照会区間・日付に照合してから保持し、両便の回答席数を希望人数で絞り込む。進捗・中止・各方向の確認時刻・0席表示・片道／往復CSVを提供する。人数を指定した旅程全体の予約可否照会や、会員優先枠の確認ではない。

### 自動接続の実証

2026年9月23日00:01（日本時間）に、MileFinderの実画面から2026年10月1日の東京〜ホノルルを照会した。照会ボタン、ローカルNode.jsサーバー、ANA公開チャットのHTTP・WebSocket、応答解析、UI表示の一連の動作に成功し、NH186便・羽田21:55発・ホノルル行き・エコノミー2席を確認した。表示された1名20,000マイルは既存チャートの計算値であり、チャット回答の価格ではない。結果は `partial: true` で、公式ブラウザの同条件の回答と一致した。

初回のNode.js試行では公開設定のGETがHTTP 403となった。実際のブラウザで観測した `User-Agent` を要求へ追加した後に解消し、上記の取得へ成功した。上流通信への `Origin` の追加は行わずに動作した。

10月1〜2日の追加試験では、一度ANAチャットの回答待ちが時間切れとなった。UIは取得失敗を表示し、空席なしへ変換しなかった。常時取得できる安定した一般公開APIとしての保証はない。失敗した段階を調べるため、固定の会話段階名と取得ページ数だけを返す診断を追加した。認証値や外部応答の全文は診断に含めない。

同条件の再照会は2026年9月23日00:20（日本時間）に成功した。MileFinderの画面で10月1日のNH186・2席と、10月2日のNH184・4席、NH182・9席、NH186・6席を表示した。いずれもエコノミー、1名20,000マイルの計算値。指定期間外の回答は表示されず、取得できた回答のうち人数を満たす4件として表示した。pingや送信タイミングを変更せずに成功したため、先の時間切れの原因は断定していない。

その後の往復試験でも、最初の「ログイン確認」待ち・取得0ページで時間切れを確認した。記録済みブラウザ通信は `Bot_Active` → `Session_Start` → 初回メッセージの順だったため、自動接続も会話開始通知を待つ順序へ合わせた。早着した開始通知も保持し、30秒の待機上限、error・close・abortで待機を終了する。初回送信の順序とタイマー解除を含む接続処理19テストが成功した。接続直後の競合が時間切れの根本原因かは確定していない。

## 会員連携の実装と既知の制約

`src/lib/memberBridge.ts` に、ログイン済みのANAフライト一覧からローカルMileFinderを開くブックマークレットを実装した。ユーザーが保存した「ANA会員検索を接続」をANAタブで実行し、新しいMileFinderから検索条件を送る。接続中はANAタブを開いたままにする。2026年9月23日02:29（日本時間）、MileFinderからANAタブへの要求、フォームPOST、同一Originへの302と結果GET、HTMLのliteral解析、検証済み項目の `postMessage`、UI表示までの一連の処理に成功した。単日の1名・2名照会は実証したが、複数日の連続取得は安定性の確認が残る。

接続は `https://aswbe-i.ana.co.jp` の国際往復の結果画面に限定する。`reSearchForm` の実際のactionと検索ボタンのname/valueを使い、同一Originの `award_search_roundtrip_result_owd.xhtml` へ `application/x-www-form-urlencoded` のPOSTを送る。観測したPOST後の302に対応し、`mode: 'same-origin'` と `redirect: 'follow'` で同一Originの結果取得に追従する。別Originへのリダイレクトは拒否する。認証と状態値はANAタブに保持し、返却HTMLの結果見出し・次の再検索フォーム・返却条件を確認してから解析する。成功画面にも非表示のセッション終了モーダルが常在するため、本文全体の文言だけで認証切れとせず、結果見出しと再検索フォームを優先するよう修正した。成功時には返却された状態を次の検索へ引き継ぎ、送信後に失敗・中止した場合は古い状態で後続検索を送らない。

出発地・目的地は接続時の路線に固定する。対象は収録済みの日本発国際線・往復・エコノミー・成人1〜9名で、各方向1区間のANA便・予約クラス `X` を採用する。`src/MemberAvailabilityPanel.tsx` は最大7出発日分を1件ずつ順番に照会し、続きは次の操作で取得する。往路・復路は各現地出発日を検証する。TYOでは公式の推薦旅程にある羽田発・成田着も認め、匿名チャットの同一具体空港へ戻る組み合わせとは区別する。

接続時に表示中の公式画面を解析し、最初の有効な照会が区間・往復日付・クラス・人数まで完全一致した場合は、その結果のスナップショットを1回だけ返して重複POSTを避ける。確認時刻は接続時の取り込み時刻を保持し、再検索時刻へ更新しない。異なる条件や後続の照会へ古い結果を再利用しない。

応答HTMLはライブDOMへ追加せず、`template.content` の中でフォームを読み取る。これにより画像・iframe・CSSによる追加通信と応答scriptの実行を防ぐ。応答HTMLで空だった空港表示名2項目は、公式画面のJavaScriptが補完していたため、接続時のライブフォームにある公開表示名を保持して各POSTへ補完する。成人のみの検索では `hiddenDomesticChildAge` を `false` にし、フォーム本文は `URLSearchParams` が自動設定するUTF-8の形式で送る。これらは安全性と観測した送信形式を合わせる修正であり、連続照会の安定取得を保証する根拠とはしない。

`src/lib/anaMember.ts` は、`createOutboundSegmentInfoMap`・`createInboundSegmentInfoMap`・`resetData` 内の観測済みliteral呼出を、外部JavaScriptを実行せず解析する。便IDで区間と推薦旅程を結び、席数・必要マイル・税金等の円額を取り出す。料金は全員合計のため再乗算しない。未知形式や対応旅程が0件の場合は例外とし、空席なしと断定しない。入力サイズ・呼出件数・構造の深さに上限を置いている。

応答HTML全文・Cookie・認証値・画面状態をローカル側へ送らない。ブリッジは区間・日付・便名・席数・全員分の料金・確認時刻などの検証済み項目だけを `postMessage` で渡し、双方でOriginと相手ウィンドウを確認する。接続時にUUIDの `connectionId` を生成し、通知に含めて照合する。古いMileFinderウィンドウの終了・中止通知などが新しい接続へ影響しないよう、不一致の通知を拒否する。`src/lib/memberResults.ts` は受信した条件と旅程を再検証する。結果と会員CSVは部分取得・発券未確認として扱い、0席や空席待ちを人数充足に含めない。ログイン切れ・画像認証・未知応答・通信失敗は再接続が必要な状態として表示する。
